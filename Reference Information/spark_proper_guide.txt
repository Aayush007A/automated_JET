SPARK JET  
 
Full Workflow Development Plan  
 
Manager Review / Proposed End-to-End Workflow  
 
  
 
1. Purpose and Scope  
 
This document consolidates the three provided SPARK JET source documents into one step-wise development workflow. It describes the intended end-to-end flow from user access and file upload, through Trial Balance and Population preparation, data cleaning, mandatory data checkpoints, Integrity Testing, Parameter Testing, Control Sample Dump, output consolidation, download, and final visualization.  
 
The workflow below is based only on the provided SPARK JET workflow notes, SPARK JET application-flow document, and the supplied Spark code. It is intended to serve as the development plan to be reviewed with the manager before implementation.  
 
2. End-to-End Workflow at a Glance  
 
1. Account / Login → Admin or User  
 
2. Input File Selection → Select Trial Balance (TB) and Population sheets from uploaded file  
 
3. Column Mapping → Map source columns to standard JET headers  
 
4. Data Cleaning → Apply field-specific trimming, numeric conversion, date conversion and text cleanup  
 
5. Data Checkpoints → Validate required data conditions; on failure show an error and discontinue processing  
 
6. Standardized Data Output → Prepare TB and Population as CSV inputs  
 
7. Integrity Testing → Run Spark processing and generate Integrity Results / exceptions  
 
8. Integrity Review Gate → Verify Test 1, Test 2, Test 3 and Test 4; obtain tickmarks/review before continuing  
 
9. Parameter Inputs → Prepare Ex1–Ex12 inputs according to the defined rules  
 
10. Parameter Testing → Run Ex1–Ex12 and validate exception outputs  
 
11. Control Sample Dump → Generate requested sample documents and validate count / balance  
 
12. Output Consolidation → Integrate engagement details and test outputs into the macro output  
 
13. Download → Provide a button to download the macro output file  
 
14. Visualization → Present reconciled/unreconciled accounts and other standard visualizations  
 
3. User/Application Flow  
 
Account/Login page with Admin/User access.  
 
After login, the user is redirected to the applicable pages.  
 
The user uploads the input file and selects the Trial Balance sheet and Population sheet.  
 
The system maps uploaded columns to the standard JET headers.  
 
The system performs data cleaning and then runs the defined data checkpoints.  
 
If a checkpoint fails, the system displays a pop-up error message with a description of the error and discontinues processing.  
 
If the data passes the required checkpoints, the workflow proceeds to Integrity Testing, followed by Parameter Testing.  
 
The application ultimately provides consolidated output, a download option for the macro output, and visualization.

6. Spark Processing / Standardization Flow  
 
The supplied Spark code implements the data-processing foundation. It reads CSV input, applies the specified transformations, creates standardized views, performs aggregation and joins between Population and Trial Balance, runs exception logic, and writes CSV outputs.  
 
Population is read from CSV with headers and comma delimiter.  
 
Source fields are trimmed and mapped into standardized fields including G_L, DocumentNo, Type, Entry_Date, Pstng_Date, Doc_Date, Amount_in_local_cur, currency fields, document/text fields and User_name.  
 
Dates are parsed and formatted as dd-MMM-yy.  
 
Amount fields are converted to numeric values after removing commas.  
 
Document header and Text commas are replaced with spaces; Text is converted to lower case in the supplied code.  
 
A total sum of Amount_in_local_cur is calculated as a processing check.  
 
Population and Trial Balance are then loaded into standardized processing structures.  
 
Null values are filled in selected processing columns before exception logic.  
 
Population is aggregated by GL to create GL-level local-currency activity used by Integrity Testing.  
 
The supplied code also writes CSV outputs for control samples, integrity results and parameter results.  
 
7. Integrity Testing  
 
Integrity Testing starts after TB and Population are prepared. The workflow notes specify running the code, checking the G/L length between Population and Trial Balance, writing the output, and filling the integrity macro.  
 
Run the Spark integrity processing.  
 
Check whether the length/count of G/L is consistent between Population and Trial Balance as specified.  
 
Generate the Integrity Result outputs.  
 
Populate the integrity macro with Basic Inputs and the extracted Test 1, Test 2 and Test 3 results.  
 
Perform the four integrity checks.  
 
After receiving tickmarks, send the results for verification.  
 
Only after review/verification proceed to Parameter Testing.

Aggregate Population Amount in local currency by GL and compare with the Integrity Result GL Activity; the workflow specifies Pivot Table + VLOOKUP verification.

Test 4 / IR Exception 4

The sum of the count plus the sum of GLs appearing in Test 3 should match exactly with the Population count.

16. Manager Review Summary  
 
The planned SPARK JET system is an end-to-end data-processing and testing workflow in which raw TB and Population inputs are standardized, cleaned and checkpointed before any testing is allowed to proceed. Integrity Testing establishes the Population-to-Trial-Balance relationship and is followed by a review gate. Parameter Testing then runs Ex1–Ex12 using the defined inputs and exception logic. Control Samples are handled as an additional requirement when requested. Finally, the generated results are consolidated into the required macro output, made downloadable, and presented through reconciliation / exception visualizations.  
 
17. Important Source-Based Notes for Development  
 
Checkpoint failure is explicitly defined as a hard stop in the application flow: show a pop-up error with the error description and discontinue processing.  
 
The workflow explicitly places Integrity Testing before Parameter Testing and requires verification/tickmarks before moving forward.  
 
The provided code contains more detailed implementation stages than the high-level application document, including null handling, GL-level aggregation, control-sample generation, individual parameter exception processing, and output-folder cleanup.  
 
The source documents do not specify a final UI technology, deployment architecture, database, authentication provider, API framework, or hosting platform. Those implementation choices are therefore outside this source-based workflow plan.  
 
The source documents also do not define the exact final visualization designs; they specify reconciled/unreconciled accounts and other standard visualizations.
